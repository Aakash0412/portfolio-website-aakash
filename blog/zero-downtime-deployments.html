Zero-Downtime Deployments on AWS

📅 Jan 2026 ⏱ 8 min read

Deploying code shouldn't mean crossing your fingers and hoping nothing breaks. In any serious production environment, deployments need to be invisible to users. No 503 errors, no "maintenance mode" pages, no dropped connections.

This post explores three deployment strategies I've used on AWS — their tradeoffs, when to use each, and the infrastructure pieces that make them work.

Why Zero-Downtime Matters

Downtime during deployments isn't just a technical inconvenience — it has real business impact. Every second of unavailability erodes user trust, affects SEO rankings, and can trigger SLA violations. The goal is to make deployments a non-event.

Strategy 1: Blue-Green Deployments

The idea is simple: maintain two identical environments — Blue (current production) and Green (new version). Deploy the new code to Green, run your smoke tests, and then flip the load balancer to point at Green.

How It Works on AWS

  • ECS + ALB — Run two ECS services behind an Application Load Balancer. Each service points to a different target group.
  • Route 53 weighted routing — Shift DNS traffic from one target group to another.
  • Elastic Beanstalk — Has built-in blue-green support via the "Swap environment URLs" feature.

Tradeoffs

Blue-green gives you instant rollback — if Green has issues, flip back to Blue. The downside is cost: you pay for two full environments during the transition window. For most teams, this window is short (minutes), so the cost is manageable.

Strategy 2: Canary Releases

Instead of switching all traffic at once, canary releases send a small percentage (e.g., 5%) of traffic to the new version. You monitor error rates, latency, and business metrics. If everything looks healthy, you gradually increase traffic until the new version handles 100%.

# AWS CodeDeploy canary config
deployment_config:
  type: Canary
  canary_percentage: 10
  canary_interval: 5   # minutes
  
# Traffic shifts:
# 0min  → 10% new, 90% old
# 5min  → 100% new (if healthy)

When to Use Canary

Canary is ideal when you need confidence before full rollout. It's especially valuable for:

  • Changes to payment or checkout flows
  • Database schema migrations that affect queries
  • Third-party API integration updates

Strategy 3: Rolling Updates

Rolling updates replace instances one at a time (or in batches). While one batch is being updated, the remaining instances continue serving traffic. This is the default strategy for most ECS and Kubernetes deployments.

Configuration

# ECS service rolling update settings
deployment_configuration:
  minimum_healthy_percent: 50
  maximum_percent: 200

# This means:
# - At least 50% of tasks stay running during deploy
# - Up to 200% of tasks can run temporarily (old + new)

Tradeoffs

Rolling updates are cost-efficient — you don't need a fully duplicate environment. But rollbacks are slower: you have to re-deploy the previous version through the same rolling process.

Choosing the Right Strategy

There's no universal answer. Here's how I think about it:

  • Blue-green → When you need instant rollback and can afford temporary double-capacity
  • Canary → When the change is risky and you want gradual validation
  • Rolling → For routine, lower-risk deployments where cost matters

"The best deployment is the one nobody notices."

Infrastructure Essentials

Regardless of which strategy you choose, these AWS components are critical:

  • Health checks — ALB health checks ensure only healthy instances receive traffic. Configure both path-based and grace period settings.
  • Connection draining — When deregistering old instances, give in-flight requests time to complete before terminating.
  • CloudWatch alarms — Automatic rollback triggers based on error rate spikes or latency thresholds.

Final Thoughts

Zero-downtime deployments aren't just for large-scale operations. Even small projects benefit from the discipline of automating safe deployments early. Once you've set up the pipeline, every future deployment becomes a non-event — and that's exactly the point.
